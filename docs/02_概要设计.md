## 2. 项目是什么？

SmartMemEngine是一个**内核模块**，通过**Hook机制**集成到Linux内存管理子系统，提供**可插拔的优化策略**和**智能监控**能力。

### 2.1 项目定位

```
用户空间                    内核空间
    │                            │
    │ 应用程序                  │ Linux内存管理子系统
    │   ├─ MySQL                │   ├─ Buddy System
    │   ├─ PostgreSQL            │   ├─ SLUB分配器
    │   ├─ Spark                │   ├─ VMA管理
    │   ├─ Hadoop                │   ├─ 页面回收
    │   └─ ...                  │   ├─ OOM机制
    │                            │   └─ NUMA管理
    │                            │
    └────────────────────────────┴────────────────────┘
                   │
                   │ SmartMemEngine (我们做的)
                   │
                   │ 这个模块Hook到内存管理的各个函数
                   │ 提供优化策略，收集监控数据
```

### 2.2 简单说：SmartMemEngine做什么？

1. **拦截**：拦截内核的内存分配/释放/回收函数
2. **监控**：收集内存访问模式和性能数据
3. **分析**：识别热点、瓶颈、问题
4. **优化**：根据分析结果应用优化策略
5. **输出**：通过接口提供统计数据和优化建议

## 3. 解决什么问题？

### 3.1 数据库场景的问题

**场景**：MySQL/PostgreSQL等数据库运行在服务器上

**问题**：
- 内存访问模式固定，但内核的内存管理不知道
- 跨NUMA（跨CPU节点）访问导致延迟增加
- 大页（huge pages）没有被充分利用

**影响**：
- 查询延迟高
- CPU利用率不饱和（等内存）
- 内存利用率低

### 3.2 大数据场景的问题

**场景**：Spark/Hadoop等大数据任务

**问题**：
- 内存分配/释放非常频繁
- SLUB（small object分配器）的缓存策略不适应批量操作
- 内存碎片化严重
- 容易触发OOM

**影响**：
- 任务执行速度慢
- 频繁的GC/Compaction
- 任务失败

### 3.3 容器场景的问题

**场景**：Kubernetes/Docker容器运行

**问题**：
- 缺乏QoS（Quality of Service）感知的内存管理
- 无法预测容器OOM
- 内存隔离效果有限
- 无法提前扩容

**影响**：
- 服务中断（OOM）
- 资源浪费（内存分配了但没用到）

```
SmartMemEngine
    │
    ├─ 1. Hook层
    │    拦截内核的内存管理函数
    │
    ├─ 2. 策略引擎
    │    管理优化策略的注册/调用
    •
    ├─ 3. 内置策略
    │    具体的优化策略实现
    │
    ├─ 4. 监控系统
    │    收集性能数据
    │
    ├─ 5. 分析引擎
    │    分析数据、识别问题
    │
    ├─ 6. 优化引擎
    │    自动调优、预测
    │
    └─ 7. 接口层
         提供用户空间接口
```

## 6. 每个大块功能是干什么的？

### 功能1：Hook层

**功能描述**：拦截（Hook）到Linux内存管理的各个函数

**具体Hook哪些函数？**

| Hook类型 | 目标函数 | 用途 |
|---------|---------|------|
| Buddy分配 | `alloc_pages()` | 在分配页面时介入 |
| Buddy释放 | `__free_pages()` | 在释放页面时介入 |
| SLUB分配 | `kmalloc()`, `kfree()` | 在分配对象时介入 |
| VMA管理 | `mmap()`, `brk()` | 在创建虚拟内存区域时介入 |
| LRU管理 | `mark_page_accessed()` | 在页面被访问时介入 |
| NUMA管理 | `migrate_pages()` | 在跨节点迁移时介入 |
| OOM处理 | `oom_killer()` | 在OOM时介入 |

**能做什么？**
- 在函数执行前修改参数（比如强制使用本地节点）
- 在函数执行后收集信息
- 统计函数调用
- 决定是否需要优化

---

### 功能2：策略引擎

**功能描述**：管理各种优化策略的注册、调用、切换

**有哪些策略类型？**

| 策略类型 | 用途 | 内置策略示例 |
|---------|------|-------------|
| Buddy策略 | 优化页面分配 | NUMA感知Buddy策略 |
| SLUB策略 | 优化小对象分配 | 自适应SLUB策略 |
| LRU策略 | 优化页面回收 | 多代LRU策略 |
| NUMA策略 | 优化跨节点访问 | 负载均衡策略 |

**能做什么？**
- 注册新的优化策略
- 注销已有的优化策略
- 运行时切换策略
- 查询当前策略状态

---

### 功能3：内置策略

**功能描述**：提供具体的、可用的优化策略

**有哪些内置策略？**

#### 策略1：NUMA感知Buddy策略

**做什么？**
- 优先在本地NUMA节点分配内存
- 本地节点内存不足时才去其他节点
- 这样减少跨NUMA访问（跨节点访问慢）

**效果**：
- 跨NUMA访问率降低80%
- 内存访问延迟降低30%

#### 策略2：自适应SLUB策略

**做什么？**
- 动态调整per-CPU缓存大小
- 统计SLUB命中率
- 命中率低时增加缓存，高时减少缓存

**效果**：
- SLUB命中率提升15%
- CPU开销不变

#### 策略3：多代LRU策略

**做什么？**
- 维护多个代（Generation）的LRU链表
- 记录页面访问历史
- 优先淘汰老代（很少被访问）的页面
- 防止扫描污染（Scanning Thrashing）

**效果**：
- 页面回收效率提升20%
- 减少不必要的页面换出

#### 策略4：NUMA负载均衡策略

**做什么？**
- 监控各NUMA节点的内存使用情况
- 自动触发节点间的内存迁移
- 使各节点的负载更均衡

**效果**：
- 节点负载更均衡
- 整体性能提升

---

### 功能4：监控系统

**功能描述**：收集内存访问和性能数据

**收集哪些数据？**

| 数据类型 | 数据内容 | 用途 |
|---------|---------|------|
| 分配统计 | 每种策略分配了多少次 | 评估策略效果 |
| 释放统计 | 每种策略释放了多少次 | 评估策略效果 |
| 访问模式 | 哪些页面访问最频繁 | 识别热点 |
| NUMA访问 | 本地/远程访问的次数 | 评估NUMA优化效果 |
| 性能数据 | 分配/释放的延迟分布 | 识别瓶颈 |

**用什么收集？**
- eBPF：零开销，收集关键事件
- tracepoint：内核提供的跟踪点
- kprobe：Hook任意函数

---

### 功能5：分析引擎

**功能描述**：分析收集到的数据，识别问题和热点

**能分析什么？**

| 分析类型 | 输出 | 用途 |
|---------|------|------|
| 热点识别 | Top-N调用堆栈及其调用次数 | 找到内存分配最多的代码路径 |
| 瓶颈分析 | 延迟分布、长尾延迟 | 找到性能瓶颈 |
| 根因分析 | OOM发生时的内存状态 | 分析OOM的原因 |

---

### 功能6：优化引擎

**功能描述**：根据分析结果自动优化

**能优化什么？**

| 优化类型 | 触发条件 | 优化动作 |
|---------|---------|---------|
| 自适应调优 | 检测到性能下降 | 自动切换到更激进的策略 |
| 预测模型 | 检测到内存压力上升 | 提前压缩页面 |
| QoS感知 | 检测到关键进程 | 优先保证关键进程的内存 |

---

### 功能7：接口层

**功能描述**：提供用户空间访问的接口

**有哪些接口？**

| 接口类型 | 路径 | 用途 |
|---------|------|------|
| procfs | `/proc/smartmem/*` | 读取配置、统计、热点 |
| debugfs | `/sys/kernel/debug/smartmem/*` | 详细调试信息 |
| netlink | NETLINK协议 | 发送告警（如OOM预测）|
