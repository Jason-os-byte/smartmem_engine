## 3. Hook层详细设计

### 3.1 Hook层是什么？

Hook层负责**拦截（Hook）**内核内存管理的各个函数，在每个函数执行前后介入。

### 3.2 Hook层由哪些子模块构成？

```
Hook层
├── buddy_hook.c      # Buddy分配/释放Hook
├── slub_hook.c       # SLUB分配/释放Hook
├── vma_hook.c        # VMA（虚拟内存区域）Hook
├── reclaim_hook.c    # 页面回收Hook
├── oom_hook.c        # OOM（内存不足）Hook
└── numa_hook.c       # NUMA（多节点）Hook
```

### 3.3 buddy_hook.c 是什么？Hook哪些函数？

**buddy_hook.c的职责**：拦截Buddy分配器（mm/page_alloc.c）

**Hook哪些函数？**

| 目标函数 | Hook方式 | 作用 |
|---------|---------|------|
| `alloc_pages()` | kprobe + kretprobe | 在分配页面时介入 |
| `__free_pages()` | kprobe | 在释放页面时介入 |

**具体怎么Hook？**

```
分配流程：
    用户调用 alloc_pages()
         │
         ▼
    [kprobe入口] buddy_alloc_entry
         │  捕获参数：order, gfp_mask
         │
         ▼
    [原函数执行] 真正的分配
         │
         ▼
    [kretprobe返回] buddy_alloc_return
         │  捕获结果：分配的page
         │
         ▼
    [策略调用] buddy_pre_alloc / buddy_post_alloc
         │  根据策略优化
         │
         ▼
    返回结果
```

**buddy_hook.c包含的函数**：

| 函数名 | 作用 |
|--------|------|
| `buddy_hook_init()` | 初始化Buddy Hook |
| `buddy_hook_exit()` | 清理Buddy Hook |
| `buddy_alloc_entry()` | alloc_pages入口Hook |
| `buddy_alloc_return()` | alloc_pages返回Hook |
| `buddy_free_entry()` | __free_pages入口Hook |

### 5.3 numa_buddy.c 是什么？

**策略名**：numa-aware

**策略描述**：NUMA感知的Buddy分配策略

**解决什么问题**：
- 默认的Buddy分配不考虑NUMA
- 导致大量跨节点访问，延迟增加

**核心思想**：
1. 优先在本地NUMA节点分配内存
2. 只有本地节点内存不足时才去其他节点
3. 这样可以最大程度减少跨NUMA访问

**如何实现**（在pre_alloc回调中）：

```c
static int numa_buddy_pre_alloc(int order, gfp_t gfp_mask, int nid)
{
    // 如果是重要的分配（可以等待）
    if (!(gfp_mask & __GFP_RECLAIM) &&
        !(gfp_mask & __GFP_RETRY_MAYFAIL)) {

        // 强制在本地节点分配
        if (!nid && (gfp_mask & __GFP_RECLAIMABLE)) {
            gfp_mask |= __GFP_THISNODE;
        }
    }
    return 0;  // 继续分配
}
```

**如何实现**（在select_node回调中）：

```c
static int numa_buddy_select_node(int preferred_nid, gfp_t gfp_mask)
{
    int nid;

    // 优先使用首选节点
    if (preferred_nid >= 0) {
        if (node_has_enough_memory(preferred_nid, gfp_mask)) {
            return preferred_nid;
        }
    }

    // 使用本地节点
    nid = numa_node_id();
    if (node_has_enough_memory(nid, gfp_mask)) {
        return nid;
    }

    // 找下一个有足够内存的节点
    nid = numa_find_next_node_with_memory(nid, gfp_mask);
    if (nid >= 0) {
        return nid;
    }

    // 回退到默认行为
    return preferred_nid;
}
```

### 5.4 adaptive_slub.c 是什么？

**策略名**：adaptive

**策略描述**：自适应的SLUB缓存策略

**解决什么问题**：
- SLUB的per-CPU缓存大小是固定的
- 不能适应不同的访问模式

**核心思想**：
1. 动态统计缓存命中率
2. 命中率低时增加缓存大小
3. 命中率高时减少缓存大小
4. 这样可以自动找到最优的缓存大小

**如何实现**（在post_alloc回调中）：

```c
static void adaptive_slub_post_alloc(void *object, size_t size)
{
    struct slub_strategy *s = slub_strategy_get();

    // 更新统计
    atomic64_inc(&s->alloc_count);

    // 计算命中率
    if (is_percpu_cache_hit(object)) {
        atomic64_inc(&s->hit_count);
    } else {
        atomic64_inc(&s->miss_count);
    }

    // 计算命中率
    u64 total = atomic64_read(&s->alloc_count);
    u64 hits = atomic64_read(&s->hit_count);
    double hit_rate = total > 0 ? (double)hits / total : 0.0;

    // 自适应调整
    if (hit_rate < 0.8 && s->cache_size < 128) {
        // 命中率低，增加缓存大小
        s->cache_size *= 2;
        pr_info("adaptive: increasing cache size to %u\n", s->cache_size);
    } else if (hit_rate > 0.95 && s->cache_size > 32) {
        // 命中率很高，减小缓存大小
        s->cache_size /= 2;
        pr_info("adaptive: decreasing cache size to %u\n", s->cache_size);
    }
}
```

### 5.5 multi_gen_lru.c 是什么？

**策略名**：multi-gen

**策略描述**：多代LRU策略

**解决什么问题**：
- 传统LRU只记录最后一次访问时间
"不能区分经常访问和偶尔访问的页面
- 容易产生Scanning Thrashing（扫描污染）

**核心思想**：
1. 维护多个代（Generation）的LRU链表
2. 页面被访问时从老代移到新代
3. 淘汰时优先淘汰最老的代
4. 这样可以保护热点页面

**数据结构**：

```c
struct mg_lru_page {
    struct page *page;         // 对应的页面
    int generation;            // 所在的代
    u64 last_access;           // 最后访问时间
    struct list_head list;      // 链表节点
};
```

**如何实现**（在page_activated回调中）：

```c
static void mg_lru_page_activated(struct page *page, bool file)
{
    struct mg_lru_page *mg_page;

    // 获取或创建LRU信息
    mg_page = get_mg_lru_page(page);
    if (!mg_page)
        return;

    // 更新访问时间
    mg_page->last_access = jiffies;

    // 从老代移到新代
    list_del(&mg_page->list);
    mg_page->generation = CURRENT_GENERATION;
    list_add_tail(&generation_list[mg_page->generation], &mg_page->list);
}
```

### 5.6 numa_balance.c 是什么？

**策略名**：load-balance

**策略描述**：NUMA负载均衡策略

**解决什么问题**：
- 某些NUMA节点内存压力大，其他节点空闲
- 导致负载不均衡，整体性能下降

**核心思想**：
1. 定期检查各NUMA节点的内存使用情况
2. 找到压力最大的节点
3. 找到压力最小的节点
4. 把一些页面从高压节点迁移到低压节点

**如何实现**（在balance回调中）：

```c
static void numa_balance(void)
{
    int max_load_node = -1;
    int min_load_node = -1;
    u64 max_usage = 0;
    u64 min_usage = U64_MAX;

    // 找到压力最大和最小的节点
    for_each_online_node(node) {
        u64 usage = get_node_memory_usage(node);

        if (usage > max_usage) {
            max_usage = usage;
            max_load_node = node->node_id;
        }

        if (usage < min_usage) {
            min_usage = usage;
            min_load_node = node->node_id;
        }
    }

    // 如果差异足够大，触发迁移
    if (max_load_node >= 0 && min_load_node >= 0 &&
        max_usage > min_usage * 2) {

        u64 migrate_size = (max_usage - min_usage) / 2;
        u64 pages = migrate_size / PAGE_SIZE;

        // 迁移页面
        for (i = 0; i < pages; i++) {
            struct page *page = find_page_to_migrate(max_load_node);
            if (page) {
                migrate_page(page, max_load_node, min_load_node);
            }
        }
    }
}
```

### 6.3 ebpf_monitor.c 是什么？

**职责**：使用eBPF实现零开销监控

**为什么用eBPF？**
- eBPF在内核中运行，性能开销极小（<0.5%）
- 可以监控内核函数的调用
- 不需要修改内核源码

**监控什么？**

| 监控项 | 如何收集 |
|--------|---------|
| 分配调用次数 | 在alloc_pages tracepoint中收集 |
| 释放调用次数 | 在__free_pages tracepoint中收集 |
| 按调用栈 | 保存调用栈的hash |
| 分配大小 | 记录分配的字节数 |

**eBPF程序示例**（简化版）：

```c
// eBPF程序
SEC("tp/mm/mm_page_alloc")
int trace_alloc(void *ctx)
{
    u64 *count;
    u64 key = 0;  // 简化版，实际可以用栈hash

    // 更新计数
    count = bpf_map_lookup_elem(&alloc_map, &key);
    if (count) {
        (*count)++;
    } else {
        u64 init = 1;
        bpf_map_update_elem(&alloc_map, &key, &init);
    }

    return 0;
}
```

**ebpf_monitor.c包含的函数**：

| 函数名 | 作用 |
|--------|------|
| `ebpf_monitor_init()` | 初始化eBPF监控 |
| `ebpf_monitor_exit()` | 清理eBPF监控 |
| `ebpf_monitor_load()` | 加载eBPF程序 |
| `ebpf_monitor_unload()` | 卸载eBPF程序 |
| `ebpf_monitor_get_stats()` | 读取eBPF统计数据 |

### 6.4 trace_monitor.c 是什么？

## 7. 分析引擎详细设计

### 7.1 分析引擎是什么？

分析引擎负责**分析收集到的数据**，识别热点、瓶颈和根因。

### 7.2 分析引擎由哪些子模块构成？

```
分析引擎
├── analysis.c       # 分析引擎核心
├── hotspot.c       # 热点识别
├── bottleneck.c   # 瓶颈分析
└── root_cause.c   # 根因分析
```

### 7.3 hotspot.c 是什么？

**职责**：识别内存分配热点

**如何识别？**

1. 统计按调用栈的分配次数
2. 计算每个调用栈的占比
3. 按占比排序，取Top-N

**数据结构**：

```c
struct hotspot {
    unsigned long stack_hash;        // 调用栈的hash
    u64 call_count;                 // 调用次数
    u64 total_size;                // 总分配大小
    double percentage;             // 占比
    unsigned long stack[16];       // 调用栈样本
};
```

**hotspot.c包含的函数**：

| 函数名 | 作用 |
|--------|------|
| `hotspot_init()` | 初始化热点识别 |
| `hotspot_exit()` | 清理热点识别 |
| `hotspot_add()` | 添加一次调用（从监控） |
| `hotspot_get_top_n()` | 获取Top-N热点 |

### 7.4 bottleneck.c 是什么？

**职责**：分析性能瓶颈

**分析什么瓶颈？**

| 瓶颈类型 | 如何识别 |
|---------|---------|
| 分配延迟高 | 统计分配延迟的分布 |
| 释放延迟高 | 统计释放延迟的分布 |
| 跨NUMA访问多 | 统计远程访问占比 |
